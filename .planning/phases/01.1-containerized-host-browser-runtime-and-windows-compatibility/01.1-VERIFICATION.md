# Phase 01.1 — actual Windows evidence with acceptance gates open

CDP readiness/session, separate no-browser Docker image, bridge Compose fixture harness, strict no-reuse configuration, owned Windows launcher, helper tests and runtime documentation are implemented. Original BrowserSession/reader/actor sources remain unchanged.

Verified on Linux: malformed endpoint/metadata/deadline contracts; real dedicated Chrome attach/read/fill/click/observable list effect; disconnect and failed-navigation survival; image build and two passing container bridge tracer/cleanup tests. The Linux bridge test uses an explicitly owned, bridge-bound diagnostic TCP relay because Linux Chrome binds loopback. This relay is not shipped in the Windows runtime and does not validate Docker Desktop host forwarding. Compose/container/network teardown completed after both failed and passing runs; temporary test profiles are removed with bounded retries after Chrome flushes.

Bridge testing found Chrome rejects DNS aliases in Host headers. Node fetch ignores Host overrides, so the native HTTP(S) readiness client sends a fixed localhost Host header, caps the response and keeps certificate validation. CDP websocket connection uses the same fixed header. Connections still go only to the explicitly configured authority. Real HTTP-header and real container tests cover both boundaries.

PowerShell helper contracts pass on Linux PowerShell 7.4.22 (official release asset SHA-256 verified) and Windows PowerShell CI. Actual Windows Server 2022 / Chrome Stable 157 / Docker Desktop 4.98 WSL2 evidence now covers discovery, real profile/alias rejection, quoting, ownership, bridge semantic execution without host Node/pnpm, disconnect survival and normal/error/build-interrupt/test-interrupt/container-stop cleanup. RUNTIME-01/02/05 are verified for the tested configuration.

The Windows startup Ctrl-C test exposed an owned-Chrome leak before CIM ownership capture (3/3 baseline). Retaining the returned process fixed that window, but a deeper probe reproduced a second gap inside the cancellable Start-Process cmdlet (30/30). Final correction `67b6098fe2197c3c08c1a598004f2657d3400a2a` retains a preallocated .NET process before starting it and reconstructs ownership through the unchanged fresh identity check. It passed 12/12 actual Chrome startup-interruption trials, full semantic execution, native launch failure, occupied-port retry/refusal and later build/test/container-stop cleanup. RUNTIME-04/06 are now verified for the documented tested paths.

RUNTIME-03 remains open: firewall profiles on the Windows VM were disabled, so rule lifecycle and connectivity do not prove enforcement; Docker Desktop actually proxies CDP through loopback rather than the WSL subnet. Forced host termination, Windows 10/11 and other backends remain unverified. The exact native instruction inside Chrome's Start call was not directly targeted; the console-interruption mechanism probe and broad real Chrome sweep are the available evidence. Do not claim blanket Windows compatibility or complete lifecycle safety. See `01.1-WINDOWS-EVIDENCE.md` and `docs/windows-cdp-runtime.md` for scope, observations and remaining gates.
