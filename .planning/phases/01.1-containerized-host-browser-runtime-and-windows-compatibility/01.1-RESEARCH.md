# Phase 01.1: Containerized Host-Browser Runtime and Windows Compatibility - Research

**Researched:** 2026-09-15  
**Domain:** Dockerized Node/Playwright client attaching over CDP to a separately launched Windows Chrome  
**Confidence:** MEDIUM — the Playwright/CDP and Docker contracts are documented and the Phase 1 baseline runs locally, but Windows Chrome, Windows Firewall, and Docker Desktop were not executable in this Linux session.

## Summary

Phase 1 already owns the semantic browser surface: `BrowserSession` launches a persistent context itself, `SemanticPageReader` reads `ariaSnapshot` YAML, and `SemanticActor` performs fail-safe semantic actions. [VERIFIED: packages/browser/src/session.ts:58-65,113-121] The inserted phase should add a separate runtime mode rather than silently changing that launch path: PowerShell owns a dedicated Windows Chrome process and profile; the container only discovers a verified CDP endpoint and attaches with `chromium.connectOverCDP`. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

The highest-risk integration detail is endpoint rewriting. Playwright’s CDP HTTP flow fetches `/json/version/` and then connects to the returned `webSocketDebuggerUrl`; Chrome commonly reports a loopback websocket URL. [VERIFIED: node_modules/.pnpm/playwright-core@1.62.1/node_modules/playwright-core/lib/coreBundle.js:42676-42694] If the fetch originates in a Linux container, an unmodified `ws://127.0.0.1:...` points back into the container, not to Windows. The adapter must validate the response and rewrite only the websocket host/port to the configured Docker host endpoint before calling `connectOverCDP`.

The recommended test shape is a single-owner integration harness: the Windows script starts Chrome with a non-standard dedicated `--user-data-dir`, a configured CDP port, and a narrowly controlled listener; the container connects through `host.docker.internal`; the fixture server is owned by the container test process and published to Windows loopback. Do not reuse an unknown CDP listener, do not kill every `chrome.exe`, do not mount the daily-driver profile, and do not add stealth tooling. [CITED: https://developer.chrome.com/blog/remote-debugging-port] [CITED: https://docs.docker.com/desktop/features/networking/networking-how-tos/]

**Primary recommendation:** add an explicit `HostChromeLauncher`/CDP adapter plus a dedicated Windows integration test profile; keep the existing `BrowserSession` path unchanged and make every startup, attach, fixture, and cleanup failure fail closed.

### Pattern 1: Attach-only browser lifecycle

**What:** Connect to an already-running Chromium browser, select `browser.contexts()[0]`, select or create a page, and disconnect the Playwright client without pretending it owns Chrome. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

**When to use:** Whenever Chrome is explicitly launched outside the container. Planner recommendation: do not call `launchPersistentContext` in this mode because the Windows profile is not the container’s filesystem and must remain host-owned. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

```typescript
import { chromium } from 'playwright';

export async function attachToHostChrome(wsEndpoint: string) {
  const browser = await chromium.connectOverCDP(wsEndpoint, {
    isLocal: false,
  });
  const context = browser.contexts()[0];
  if (!context) {
    await browser.close();
    throw new Error('CDP browser exposed no default context');
  }
  const page = context.pages()[0] ?? (await context.newPage());
  return { browser, context, page };
}
// browser.close() disconnects this client; the PowerShell owner still closes Chrome.
```

Source: Playwright `BrowserType.connectOverCDP` documentation. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

### Pattern 2: Probe, validate, then normalize the CDP endpoint

**What:** Fetch `/json/version` through `host.docker.internal`, validate the JSON and websocket path, replace only the endpoint host/port, then pass the websocket URL to Playwright. The DevTools Protocol documents `Browser`, `Protocol-Version`, and `webSocketDebuggerUrl` in `/json/version`. [CITED: https://chromedevtools.github.io/devtools-protocol/#get-jsonversion]

```typescript
import { z } from 'zod';

const VersionSchema = z.object({
  Browser: z.string().min(1),
  'Protocol-Version': z.string().min(1),
  webSocketDebuggerUrl: z.string().url(),
});

export async function resolveWsEndpoint(endpoint: string): Promise<URL> {
  const base = new URL(endpoint);
  const response = await fetch(new URL('/json/version/', base));
  if (!response.ok) throw new Error(`CDP readiness returned HTTP ${response.status}`);
  const info = VersionSchema.parse(await response.json());
  const ws = new URL(info.webSocketDebuggerUrl);
  if (ws.protocol !== 'ws:' && ws.protocol !== 'wss:') throw new Error('CDP websocket scheme is invalid');
  if (!ws.pathname.startsWith('/devtools/browser/')) throw new Error('CDP websocket is not a browser endpoint');
  ws.hostname = base.hostname;
  ws.port = base.port;
  return ws;
}
```

The host rewrite is the key container rule: Playwright 1.62.1 appends `json/version/` to an HTTP endpoint and returns the JSON field directly. [VERIFIED: node_modules/.pnpm/playwright-core@1.62.1/node_modules/playwright-core/lib/coreBundle.js:42676-42694] Do not accept an endpoint supplied by page content or an arbitrary user URL; it is a local control-plane address and must come from launcher configuration. [CITED: https://chromedevtools.github.io/devtools-protocol/]

### Pattern 3: Dedicated Windows launcher with PID ownership

**What:** Resolve an executable, reject missing/non-file paths, reject profile paths under Chrome’s normal `User Data` roots, preflight the chosen port, launch with an explicit non-standard profile, poll readiness, and clean up only the captured process. Chrome 136+ ignores remote-debugging switches for the default Chrome data directory. [CITED: https://developer.chrome.com/blog/remote-debugging-port]

```powershell
param(
  [string]$ChromePath,
  [string]$ProfileDir = (Join-Path $env:LOCALAPPDATA 'Juno\ChromeProfile'),
  [int]$CdpPort = 9222
)

# Discovery implementation should fill $ChromePath before this block and verify Test-Path -PathType Leaf.
$args = '--remote-debugging-port=' + $CdpPort +
  ' --remote-debugging-address=0.0.0.0' +
  ' --user-data-dir="' + $ProfileDir + '"'
$chrome = Start-Process -FilePath $ChromePath -ArgumentList $args -PassThru

try {
  # Poll http://127.0.0.1:$CdpPort/json/version and the container-visible endpoint.
  # Run attach/read/act smoke tests before treating the launcher as ready.
}
finally {
  if ($chrome -and -not $chrome.HasExited) {
    Stop-Process -Id $chrome.Id
    Wait-Process -Id $chrome.Id -Timeout 10 -ErrorAction SilentlyContinue
  }
}
```

This uses `Start-Process -FilePath`, a single quoted `-ArgumentList` string for paths containing spaces, `-PassThru` for process ownership, and PID-based `Stop-Process`; those behaviors are documented by Microsoft. [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process] [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/stop-process]

### Pattern 4: One fixture-port owner

**What:** In the CDP integration image, let one `webServer` process own the fixture port. Make the fixture bind to the container interface, publish that port only to Windows loopback, and set `reuseExistingServer: false` in CI/integration mode. Playwright’s webServer plugin reuses an already-available server without owning it, and its Windows graceful-shutdown behavior differs from POSIX. [CITED: https://playwright.dev/docs/test-webserver]

**When to use:** Every Docker CDP test run. A manually started fixture is a separate mode, not an accidentally reused process.

| Problem | Don’t Build | Use Instead | Why |

| Browser protocol transport | A raw CDP client or custom page protocol | Playwright `chromium.connectOverCDP` | Existing contexts/pages and Phase 1 semantic APIs remain reusable. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp] |

**Key insight:** the difficult part is not CDP connection syntax; it is proving that the endpoint, profile, process, port, and fixture all belong to this run before any page action is permitted.

## Common Pitfalls

### Pitfall 1: HTTP CDP endpoint returns an unreachable loopback websocket

**What goes wrong:** The container can fetch `/json/version/`, then `connectOverCDP` tries `ws://127.0.0.1/...` inside the container.  [VERIFIED: Playwright source path and lines above; failure path is a deployment consequence]

**How to avoid:** Normalize `webSocketDebuggerUrl` to `host.docker.internal` and the configured port; test both the Windows-local and container-visible probes. [CITED: https://docs.docker.com/desktop/features/networking/networking-how-tos/]

### Pitfall 2: Chrome silently ignores CDP flags on the normal profile

**What goes wrong:** Chrome 136+ does not honor `--remote-debugging-port` or `--remote-debugging-pipe` against the default data directory. [CITED: https://developer.chrome.com/blog/remote-debugging-port]

**How to avoid:** Always pass a non-standard dedicated `--user-data-dir`; reject paths whose normalized form is a daily-driver Chrome/Chromium `User Data` root. [CITED: https://developer.chrome.com/blog/remote-debugging-port] [VERIFIED: packages/browser/src/profile.ts:25-43]

### Pitfall 3: CDP binds too broadly

**What goes wrong:** A CDP port is a browser-control interface; binding it to all host interfaces without a firewall boundary can allow an unintended machine to control the profile. [CITED: https://developer.chrome.com/blog/remote-debugging-port]

**How to avoid:** Prefer Docker Desktop host networking only when its opt-in/isolation tradeoff is accepted; otherwise use bridge networking, a configured port, a Windows Firewall rule limited to the Docker/WSL source range, and a teardown rule. If the source range cannot be determined safely, stop and require a human setup checkpoint. [CITED: https://docs.docker.com/engine/network/drivers/host/] [ASSUMED: exact Windows Firewall rule/discovery implementation]

### Pitfall 4: Port is reachable but owned by an unrelated browser

**What goes wrong:** A fixed port can already serve another Chrome, DevTools, or malicious local service; blindly attaching violates explicit-launch ownership.

**How to avoid:** Planner gate: fail if the port is occupied before launch; after launch, correlate the captured PID/profile/port with `/json/version` and refuse mismatches. Never treat “HTTP 200” alone as ownership. [CITED: https://chromedevtools.github.io/devtools-protocol/#get-jsonversion]

### Pitfall 5: Chrome path works only on one Windows installation

**What goes wrong:** User-level and system-level installs, architecture differences, and multiple Chrome channels make a single hard-coded path brittle. [CITED: https://chromium.googlesource.com/chromium/src/+/main/chrome/installer/setup/README.md]

**How to avoid:** Planner recommendation: precedence should be explicit `-ChromePath`, trusted environment/config override, `Get-Command chrome.exe` only after file validation, then a small candidate list; run `chrome.exe --version`/process metadata and report the selected path without leaking unrelated user paths. [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process] [ASSUMED: exact candidate list requires Windows validation]

### Pitfall 6: PowerShell turns a profile path into multiple arguments

**What goes wrong:** A path such as `C:\Users\Name With Spaces\...` is split or its quotes are stripped before Chrome receives `--user-data-dir`.

**How to avoid:** Use `Start-Process -FilePath` and a tested single `-ArgumentList` string with escaped/embedded quotes, or a carefully tested argument-array implementation; include spaces, apostrophes, Unicode, and trailing-backslash cases in the Windows matrix. [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process]

### Pitfall 7: Cleanup leaves Chrome or the profile locked

**What goes wrong:** `browser.close()` disconnects the Playwright client but does not own or terminate the separately launched Chrome. [CITED: https://github.com/microsoft/playwright/blob/main/tests/library/chromium/connect-over-cdp.spec.ts]

**How to avoid:** Put launcher cleanup in `finally` and Ctrl-C/error handlers; stop the captured PID, wait for exit, verify the matching process is gone, and only then remove a temporary profile. Persistent user profiles should not be deleted. [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/stop-process]

### Pitfall 8: `reuseExistingServer` hides port ownership

**What goes wrong:** Current config explicitly reuses an already-running `127.0.0.1:8931` server, so the test may be exercising stale code or a process owned by another run. [VERIFIED: packages/browser/playwright.config.ts:24-29]

**How to avoid:** Keep reuse for interactive local development only; use `false` for CI/CDP integration, unique project/container names, a deterministic fixture bind, and a post-run port check. [CITED: https://playwright.dev/docs/test-webserver]

### Pitfall 9: CDP version drift is diagnosed as a generic timeout

**What goes wrong:** Playwright documents CDP as lower fidelity than its own protocol and warns that launching Chrome without Playwright’s curated arguments can break functionality; Chrome updates can therefore break an attach smoke test without a useful product error. [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

**How to avoid:** Planner recommendation: record `Browser` and `Protocol-Version`, pin the container Playwright version, run a real attach → page URL → accessibility snapshot → semantic action smoke test, and fail with both version strings and the endpoint stage. Do not invent a major-version compatibility threshold without a tested matrix. [CITED: https://chromedevtools.github.io/devtools-protocol/#get-jsonversion] [CITED: https://playwright.dev/docs/api/class-browsertype#browser-type-connect-over-cdp]

### PowerShell discovery policy

```powershell
function Resolve-ChromePath([string]$ExplicitPath) {
  $candidates = @()
  if ($ExplicitPath) { $candidates += $ExplicitPath }
  $command = Get-Command chrome.exe -ErrorAction SilentlyContinue
  if ($command) { $candidates += $command.Source }
  # Add Windows user-level/system-level candidates only after Windows validation.
  foreach ($candidate in ($candidates | Select-Object -Unique)) {
    if (Test-Path -LiteralPath $candidate -PathType Leaf) { return (Resolve-Path -LiteralPath $candidate).Path }
  }
  throw 'Google Chrome executable was not found; pass -ChromePath explicitly.'
}
```

The explicit path and file validation are required because Microsoft warns against using untrusted data as `-FilePath`; the exact candidate paths remain a Windows test-matrix decision. [CITED: https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/start-process] [ASSUMED: exact Windows candidate paths]

## Open Questions

1. **Which Docker Desktop networking mode is approved for the first Windows test?** Bridge mode is the portable default; host networking reduces the CDP bind problem but requires an opt-in and weakens network isolation. [CITED: https://docs.docker.com/engine/network/drivers/host/]
2. **What exact Windows Firewall scope is acceptable?** The answer depends on Docker Desktop backend/WSL mode and local policy; do not lock a CIDR or rule command before a Windows run.
3. **Does the target Chrome build keep the `Start-Process` PID alive as the browser owner?** Verify with process command lines and a cleanup test; otherwise design a targeted process-tree owner record.
4. **Should the CDP port be fixed or allocated?** A fixed configured port simplifies container wiring; allocation lowers collision risk but requires a trusted handoff of the selected port and firewall rule.
5. **Should Chrome Stable or Chrome for Testing be the supported binary?** User-facing intent favors Stable; Chrome for Testing is the official automation fallback. [CITED: https://developer.chrome.com/blog/remote-debugging-port]
