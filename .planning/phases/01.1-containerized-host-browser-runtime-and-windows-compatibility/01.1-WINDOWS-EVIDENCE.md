## Startup correction

Before the first correction, `$owner` did not exist during the CIM capture loop after Chrome started. Ctrl-C could enter `finally` with no record, skip browser shutdown and release the profile lock while that Chrome remained alive. Retaining the returned process in cleanup scope fixed that window on Windows, but a deeper console-event probe showed the `Start-Process` cmdlet can itself be cancelled after spawning a child and before returning its process object (30/30 probe trials).

The stronger correction retains a preallocated `System.Diagnostics.Process` object before invoking its .NET `Start()` method and records the candidate port before launch. It therefore avoids depending on that cancellable cmdlet return. Cleanup can reconstruct a candidate record and then re-read and check PID, creation time, profile, port and run token before stopping only that tree. An allocated object that never started is handled without masking cleanup, and process handles are disposed. This does not allow killing an unknown process.

Final Windows verification of `67b6098` passed 12/12 actual Chrome startup-interruption trials and a full two-test semantic run. A console-event stress probe with the same .NET launch configuration produced no orphaned processes across two trials encompassing 2,027 process starts, compared with 30/30 orphaning trials for the cmdlet pattern. The probe is mechanism evidence; Ctrl-C cannot be targeted at the exact native instruction inside Chrome's launch. A non-PE file named chrome.exe triggered a real process-start error, which reached the caller unmasked while cleanup still removed the temporary rule and released the profile lock.

Every final launcher run left no owned Chrome, firewall rules, containers, networks or listeners on 9222/9223/9224/8931. The persistent dedicated profile and marker remained, its lock was released, and unrelated Chrome survived. The first eight sweep log lines misdecoded the Chinese profile path in two harness-only checks, giving false-negative marker/lock columns; the leak watcher was independent and unaffected. The report records that limitation and the corrected checks.

## Network boundary and remaining acceptance

The tested Docker Desktop backend forwarded container CDP traffic through `com.docker.backend` to Chrome's `127.0.0.1` listener. A WSL subnet must not be assumed to be the source Chrome observes. Successful probes and scoped-rule lifecycle on a firewall-disabled VM do not prove a firewall allow/deny policy. The observed boundary is loopback binding plus the Docker Desktop host proxy; local processes/containers inside that boundary remain trusted. RUNTIME-03 stays open pending enabled-firewall/backend boundary validation.

RUNTIME-01/02/04/05/06 are verified for the tested configuration and documented graceful/error/console-interruption paths. RUNTIME-03 keeps Phase 01.1 incomplete. Forced PowerShell/host termination cannot guarantee `finally`; Windows 10/11 and other Docker backends remain unverified. With `UseShellExecute=false`, Chrome inherits launcher stdio, so diagnostics appear in its console and a browser surviving forced termination may retain a redirected pipe. These limits are documented rather than counted as tested passes.

Minor baseline observations: refusal of an unmarked profile leaves a lock file (the handle is released), and Compose leaves per-run image tags after container/network teardown. Test-created tags and decoy profiles were removed by the verification session. Persistent Juno profiles are deliberately retained.
